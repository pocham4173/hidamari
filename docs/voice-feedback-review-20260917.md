# 本人の操作を声でも確認できるようにする改良

2026年9月17日。依頼された「10人会議」は、5つのAIレビュー担当がそれぞれ2つの立場でコードを確認して実施した。外部専門家・利用者10名による実証ではない。

## 根本原因と事実

予定の入力画面・自由返信・定型返信の成功には、すでに読み上げ処理があった。一方、本人の押し込み表現のため、クリック全体を650ms後に再実行していた。音声開始もその後になり、保存結果の声はさらに非同期の書き込み完了後だった。

[WebKit公式の音声実装](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/speech/SpeechSynthesis.cpp)には、iOSで最初の音声をユーザー操作中に開始する制限がある。今回の構造はこれに抵触し得る。利用者のiPhoneの実際の再生状態や音量までは確認していない。

画像の無効な返信ボタンは別の問題である。コード上、その文言は現在の承認済み参加者に返信先となる別の家族用アカウントを確認できない場合に出る。以前のメッセージはそのまま読める。画像だけで、相手の退出・画面変更・同じアカウントの利用のどれかを断定していない。

## 10の立場からの判断

| 立場 | 問題・反対意見 | 今回の対応 |
| --- | --- | --- |
| 1. 高齢の本人 | 押せない見出しが「返事を送る」で、操作対象に見える | 「返事を選ぶ」に変更。結果を声で聞き直すボタンを用意 |
| 2. 家族との利用 | 自由に書いた内容を送れたか分からない | 確認後に本文を引用して「返事を送りました」と読む。相手の既読とは言わない |
| 3. ブラウザー技術 | 音声開始が実際のタップから離れている | タップの同期処理で声を開始し、画面・書き込みの650msの待ち時間は維持 |
| 4. 音声の信頼性 | 新着が操作結果を中断、開始失敗で再読できなくなる | 操作結果を優先し、新着は待機。開始を確認できなければ状態を解除し再読可能に |
| 5. 品質確認 | 従来の検査は音声をスタブに置き換え、実際の押し込み経路を通らない | 実際の音声モジュールと押し込み処理、公開HTMLの操作を組み合わせて検査 |
| 6. 回帰防止 | 二重保存、旧家庭の遅延完了、書きかけ消失 | 予定の処理中・家庭・画面のガード。同じ返信先・同じセッションの草稿を保持 |
| 7. 安全性・プライバシー | オフや家庭変更後にも前の音声が続く | オフ・家庭リセット・アプリ非表示で音声と待機音声を停止 |
| 8. 通信不良・復旧 | 無効ボタンは押せず、音声も出ない | その場に「家族の参加を確認する」を表示。未確認時は再読み込み。承認条件は維持 |
| 9. サポート運用 | 設定・ヘルプに会話欄が消える旧仕様の説明が残る | ホームに常設、送信には参加確認が必要という説明へ統一 |
| 10. 長期の使い心地 | 自分のやることだけ無音、操作ごとに結果が違う | 開く・保存・できた・入力不足・失敗にも音声。自動更新は読み上げない |

## 失敗を先に想定する

1. 「声が出たから送信成功」と誤認する：最初は「送ります」「保存しています」、書き込み成功後だけ「送りました」「保存しました」と伝える。
2. 声を増やし過ぎてうるさくなる：自動読み上げは本人の設定を尊重する。履歴は開いた案内と、選んだ連絡の読み上げに分ける。家族画面へ自動音声を一律追加しない。
3. 音声が出ないと再送を繰り返す：画面の結果を残し、「結果を声で聞く」は読み上げのみで書き込みをしない。音声APIの失敗は保存失敗と混同しない。

## 目標と合格条件

- タップ直後に音声開始要求が出ること。実際の保存・遷移は押し込み表現の後に一度だけ行うこと。
- 定型返信・自由返信・予定・履歴返信の成功を、書き込み確認より前に読み上げないこと。
- 音声オフで自動音声が出ず、再生中の声も止まること。「声で聞く」の明示操作は利用できること。
- 通信未確認・未承認の送信を許可せず、別家庭へ切り替えた後に旧結果を表示・発話しないこと。
- 本人・家族の実Firestore SDKによる会話往復が引き続き通ること。

自動検査は音声APIへの発話要求と操作結果を確認する。iPhoneのスピーカーから聞こえる音そのものの実機確認とは区別する。市の正式な推奨や安全認証の取得を意味しない。

## 費用と次の確認

新しい課金サービス、音声クラウド、Firebaseの料金プラン変更は追加しない。端末ブラウザーの読み上げを使用する。音声入力・録音・写真共有の追加は今回の範囲に含めない。

公開前に操作・権限・通信の回帰検査、公開後にHTMLと変更した音声関連ファイルの実配信を確認する。実際の利用では「予定を入れる→保存」「返事を選ぶ→送信」「自由に書く→送信」「前の連絡→声で読む」の4場面を、本人が迷わず声と画面で確認できることを目標にする。
